## 实机采集（不含实体标签定位验收）

两轮各约 22 秒、独立 master，仅运行相机及视觉，结束后全部停止。
第一轮与构建有重叠，约 8.21 Hz；第二轮没有并发构建或测试，结果如下：

| 指标 | 第二轮结果 |
| --- | --- |
| 图像尺寸/格式/frame | 2560×1440 / mono8 / ov13855_optical_frame |
| 接收图像 | 171 帧 |
| 同时间戳 CameraInfo 配对 | 171/171 |
| 接收频率 | 8.306 Hz |
| 按源时间戳计算频率 | 8.292 Hz |
| 图像接收帧龄 P50 / P95 | 80.39 / 95.39 ms |
| 检测处理耗时 P50 / P95 | 34.89 / 45.67 ms |
| 已处理帧 / Pose | 170 / 0 |

处理帧与接收帧计数在采样截止瞬间可能相差一帧，不能据此认定丢帧。
GStreamer 协商 caps 是 15 FPS，实际源时间戳约 8.29 Hz；没有用 caps 冒充实测帧率。
原因尚未定位，后续应检查传感器/ISP/曝光链路及传输处理时序。

原控制配置 `pose_timeout_sec=0.1`，实际帧周期约 0.121 秒，即使后续逐帧识别，
也可能间歇触发超时。此次按约定保留原控制参数，未以放宽超时掩盖采集频率差异。
闭环使用前需解决或明确接受并配置这一帧率/超时关系；当前不宣称完成实飞验收。

原始第二轮数据保存在本目录 `validation/live_results.json`，第一轮在
`validation/live_results_initial.json`；脚本为 `test/live_camera_check.py`。
PTS 映射为采集时间估计，不是硬件曝光时间证明。

## 后续补测：用户摆放 tag36h11 / ID 0

用户提供 `tag36h11_id00000.png` 并放入视野。首次尝试时设备被用户打开的
1280×720 GStreamer 预览独占；取得用户“直接关闭”指示后，核验 PID/启动时间及程序身份，
关闭该预览，再用新链路采样；未恢复用户要求关闭的预览。

- 新相机真实采集 173 帧 2560×1440 mono8，173/173 CameraInfo 配对。
- tag36h11 / ID 0 连续检出；1 帧 DETECTED_2D（CameraInfo 首次到达前），172 帧进入位姿检查。
- 172 帧均因重投影门禁被拒绝，末尾 RMS 约 14.06–14.20 px，高于原门限 1 px。
- 位姿发布 0 帧：识别成功不等于有效位姿，门禁未被放宽。
- 接收频率 8.411 Hz；处理耗时 P50/P95=44.80/71.39 ms（本轮额外开启了标注图输出和存图）。
- 标注画面中绿色框准确包围屏幕上的码，ID 显示为 0。当前参考内参与成像几何仍需核对；
  尚无证据证明重投影超限的具体原因，不能仅靠提高误差门限宣称有效定位。
- 屏幕上实际显示的黑框边长尚未测量，不能把默认 12 mm 直接视为实物尺度。

证据：`validation/tag0_detection_results.json` 与 `validation/tag0_detected.jpg`。
